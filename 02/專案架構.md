# 校務系統 MVP 架構

## 技術棧

| 層級 | 技術 | 細節 |
|---|---|---|
| Runtime | Deno 2.9.7 | 內建 TypeScript、lint、fmt、test，不需額外安裝工具鏈 |
| 框架 | Fresh（Deno 官方全端框架，Preact） | 同一套框架處理頁面渲染與 API route，不需 Next.js |
| 資料庫 | SQLite | 單一檔案資料庫（`prod.db`），透過 Deno 內建 `node:sqlite` 模組操作，不需額外 ORM |
| 身分驗證 | bcrypt（npm 相容套件）+ JWT（JSR `djwt`） | 自行實作登入與 session，`role` 欄位放進 token payload 供中介層判斷權限 |
| 樣式 | 純 CSS | 不額外引入 Tailwind，減少建置設定 |
| 檔案儲存 | 本機 `/uploads` 目錄 | MVP 階段先用本機磁碟，附件量增加後再評估雲端儲存 |
| 部署 | Fly.io 或 Railway（Deno runtime + persistent volume） | Deno Deploy 的檔案系統不持久化（僅 Deno KV 可持久），SQLite 需要固定掛載磁碟的平台 |

## 系統分層

```
使用者（學生 / 教師 / 行政人員）
        │
        ▼
前端層：Fresh 網頁介面
        │
        ▼
後端 API 服務（Fresh route handlers）：業務邏輯與權限控管 ──▶ 外部服務：Email 通知
        │
        ▼
資料層：SQLite（單一檔案，掛載於 persistent volume）
```

## 核心模組

### 帳號與角色權限
- 三種角色：`student`、`teacher`、`admin`
- 登入採帳號密碼，密碼雜湊後儲存
- Fresh route middleware 依 JWT 內的 `role` 欄位擋下無權限的頁面與 API 呼叫
- admin 可建立/停用帳號，teacher 與 student 帳號由 admin 建立後發送初始密碼

### 學生基本資料管理
- 欄位：姓名、學號、出生日期、聯絡電話、緊急聯絡人、班級歸屬
- admin 可新增/編輯/查詢；teacher 僅能查詢自己班級學生；student 僅能查詢自己資料
- 支援依班級、學號搜尋與列表分頁

### 課程與班級管理
- 班級：班級名稱、學年度、導師（關聯 teacher）
- 課程：課程名稱、授課教師、上課時段、對應班級
- admin 建立班級與課程，teacher 可查詢自己授課的課程列表

### 成績或出缺勤（擇一先做）
**若選成績：**
- 欄位：學生、課程、學期、分數、評語
- teacher 可對自己授課課程的學生登錄與修改成績
- student 僅能查詢自己成績

**若選出缺勤：**
- 欄位：學生、課程、日期、狀態（出席/請假/缺席）、備註
- teacher 可對自己課程當日點名
- student 可查詢自己出缺勤紀錄

### 公告通知
- 欄位：標題、內容、發布對象（全校/特定班級）、發布時間
- admin 與 teacher 可發布，發布後觸發 Email 通知給對象名單
- 所有角色可在首頁看到自己相關的公告列表
- 記錄每位使用者的已讀狀態（`announcement_reads` 表），讓行政端可追蹤觸達率

### 學期管理
- 維護「目前學期」設定（`semesters` 表），成績、出缺勤、課程一律關聯到學期
- admin 可建立新學期並設定為目前學期，切換後新資料自動歸入新學期，舊學期資料保留可查詢

### 密碼重設
- 使用者於登入頁點擊「忘記密碼」，輸入 email 後寄送一次性重設連結（有效期限如 30 分鐘）
- 重設 token 存於資料庫並標記使用狀態，避免重複使用

## 資料表

```
users               id, name, email, password_hash, role, is_active, deleted_at, created_at
students            id, user_id(FK), student_no, birth_date, phone, emergency_contact, class_id(FK), is_active
teachers            id, user_id(FK), phone, is_active
classes             id, name, year, homeroom_teacher_id(FK)
courses             id, name, teacher_id(FK), class_id(FK), schedule, semester_id(FK)
enrollments         id, student_id(FK), course_id(FK)
grades              id, student_id(FK), course_id(FK), semester_id(FK), score, comment
attendance          id, student_id(FK), course_id(FK), date, status, note
announcements       id, title, content, target_class_id(FK, nullable), created_by(FK), created_at
announcement_reads  id, announcement_id(FK), user_id(FK), read_at
semesters           id, name, is_current, start_date, end_date
audit_logs          id, user_id(FK), action, target_table, target_id, detail, created_at
password_resets     id, user_id(FK), token, expires_at, used_at
```

- `role` 欄位設計成字串而非寫死的 enum 三種，日後要加家長角色時不需大改 schema，並預留學生與家長的關聯表（如 `parent_student_links`）
- 涉及成績、出缺勤等歷史資料的表（`students`、`teachers`）一律用 `is_active` 標記停用，不做實體刪除，避免歷史紀錄斷鏈
- `audit_logs` 為通用表，所有模組的敏感操作（查詢/修改個資、成績變更等）統一寫入這張表，不需每個模組各自實作

## 安全性

- 密碼以 bcrypt（cost factor 10 以上）雜湊儲存，不儲存明文
- 所有 API route 入口用 zod（JSR 相容）做 schema 驗證輸入格式
- 對登入 API 加 rate limiting（例如每 IP 每分鐘 5 次），防暴力破解
- 依角色（RBAC）在中介層統一攔截，避免每個 API 各自寫權限判斷邏輯造成疏漏
- 對學生個資的查詢與修改動作寫入 `audit_logs`（誰在何時查/改了什麼）
- SQLite 檔案定期備份（例如每日 cron 複製一份到獨立儲存空間），避免單點故障遺失資料

## 匯出功能

- 成績單、出缺勤紀錄支援匯出 CSV（MVP 先做 CSV，PDF 排版留待第二階段）
- 匯出範圍依角色限制：teacher 僅能匯出自己課程資料，admin 可匯出全校資料
- 資料表設計時已考慮好查詢欄位（如 `semester_id`），確保日後依學期篩選匯出不需改 schema

## 維運

- 開發、測試、正式環境使用各自獨立的 SQLite 檔案（如 `dev.db`、`test.db`、`prod.db`），避免測試資料污染正式資料
- 撰寫 seed script（`scripts/seed.ts`），建立測試帳號（各角色至少一組）與範例班級/課程/學生資料，加速開發與展示
- 串接 Sentry 免費方案做錯誤監控，正式環境發生例外時能即時收到通知並定位問題

## 入口頁資訊架構參考

台灣大專院校校務系統入口頁常見的分類邏輯，作為你自己設計原創版面時的參考架構（非複製特定學校版面）：

**依身分別分流**
- 教職員入口
- 學生入口
- 有時另外區分「訪客/考生」入口（查榜、招生資訊等不需登入的功能）

**依業務單位分類（常見於選單或功能列表）**
- 教務類：課程查詢、選課系統、成績查詢、學籍資料
- 學務類：獎助學金、社團活動、宿舍申請、請假系統
- 總務類：場地借用、財產申報
- 人事類：差勤、薪資（多為教職員限定）
- 資訊類：電子郵件、無線網路帳號、單一入口登入（SSO）

**共通元件**
- 單一登入（SSO）入口，通常放在頁面最顯眼位置
- 最新公告/跑馬燈區塊
- 常用系統捷徑（依使用頻率客製化排序）
- 聯絡資訊/常見問題入口（放在頁尾或側欄）

**建議套用到你的 MVP**
以你目前規劃的角色（student/teacher/admin）為基礎，入口頁可以簡化成：
- 登入後依 `role` 導向對應的儀表板，不做「身分別選擇頁」（因為系統本身已知道使用者角色）
- 首頁儀表板放：目前學期資訊、未讀公告數、常用功能捷徑（依角色不同顯示不同項目，例如 teacher 看到「點名」、student 看到「查成績」）
- 不需要仿照大型校務系統做多層選單，MVP 階段用簡單的側邊欄或頂部導覽列列出所有可用模組即可

## 開發順序

1. **資料表設計 + 帳號權限系統**：建立 SQLite schema（含 `audit_logs`、`semesters`、`is_active` 等欄位）、實作登入、密碼重設與角色中介層、撰寫 seed script
2. **學生資料、課程管理模組**：CRUD API + 對應前端頁面，含角色限制的查詢範圍與軟刪除邏輯
3. **成績/出缺勤模組**：依選定項目實作登錄與查詢功能，關聯目前學期
4. **公告通知**：發布 API + Email 通知串接 + 已讀狀態追蹤 + 首頁公告列表
5. **匯出功能**：成績/出缺勤 CSV 匯出
6. **部署至 Fly.io/Railway 測試環境並驗收**：設定 Deno runtime、persistent volume、環境變數、備份排程、Sentry 監控，跑一輪端對端測試後正式開放
